## 2. 점검 범위와 제외 사항

`requirements.md`, `decisions.md`, `security-architecture.md`, `AGENTS.md`, `README.md`, `src/live`, `src/admin`, `src/js` 엔진, `supabase/functions`, `supabase/proposals`, 관련 `tests/live`, `tests/admin`, `tests/contract`, `tests/golden`, 보고서 스냅샷과 레거시를 조사했다. 아래 경로는 별도 표기가 없으면 기준 커밋에 추적되는 로컬 파일이며 fetch한 해당 원격 브랜치에도 같은 커밋으로 존재한다. 원격 운영 배포 자산이나 DB와의 동일성은 확인하지 않았다. 실제 운영 환경의 설정·사용자 데이터·DB 쓰기·배포는 확인하지 않았다.

## 3. 상태 판정 기준

- **구현**: 기준 커밋에 요구 기능의 주요 코드 경로가 확인된다. 실제 배포, 보안 또는 동작 성공을 보증하지 않는다.
- **부분 구현**: 일부 경로는 있으나 기능·안전 경계의 중요한 부분이 없거나 적용 조건이 남아 있다.
- **미구현**: 조사한 live/서버 경로에서 해당 기능을 찾지 못했다. 레거시 데모만 있으면 이 범주다.
- **판정 보류**: 정책이 미확정이거나 요구사항 충족 판단의 근거가 부족하다.

표의 테스트 열은 관련 테스트 **파일의 존재와 이번 실행 여부**를 뜻한다. 이번 점검에서 모든 테스트는 **미실행**이다. 코드·설정·테스트 파일의 정적 확인만 수행했고, 실제 브라우저 흐름과 실제 서버·DB·운영 환경은 미검증이다. SQL 제안은 코드 저장과 실제 DB 적용을 구분한다. 우선순위는 P0 보안·무결성·운영 검증, P1 상담사 페이지네이션과 관리자 기반, P2 관리자 분석·출력, P3 고객사 후속 기능의 제안이며 일정이나 승인이 아니다. 접근 통제 미완성은 역할과 무관하게 P0으로 올렸다.

## 10. 코드·문서 간 불일치

- STEP 14-A(2026-11-06): 고객사 마스터 `client_companies`를 별도 운영 데이터로 추가했다. 아래 STEP 07의 "별도 기업 테이블 없음/기업 관리 후속" 기록은 당시 조사 이력이다. 이번 SQL은 아직 미적용이며 기존 운영 관리·진단 현황·분석의 기업 목록은 계속 `participants.company_name`에서 나온다. 두 목록을 자동 동기화하거나 고객사를 자동 생성하지 않는다.

- 상담사 목록은 `assessment`의 `readAll`이 서버 응답을 나눠 읽지만 `counselorView`는 검색·필터 후 전체 `rows.map`을 렌더링한다. 페이지 상태·이동 UI가 없어 사용자 목록 페이지네이션은 완료되지 않았다. 테스트의 “pagination”은 서버 읽기 분할을 검증한다.
- 통합 보고서는 레거시의 관리자·상담사 데모에 있으나 최신 정책은 관리자 전용이다. 운영 관리자 통합 API와 9개 분석 경로는 확인되지 않았다. 레거시 메뉴가 현행 권한을 부여하지 않는다.
- `supabase/proposals/INTEGRATION.md`는 과거 시점에 assessment 원본이 없었다고 기록하지만 현재 기준 커밋에는 `supabase/functions/secondcareer-assessment/index.ts`가 있다. 과거 기록을 현재 상태로 취급하지 않는다. 실제 배포본과의 일치도 추정하지 않는다.
- `live/survey-view.js`의 사후 화면에는 임시저장만 가능하다는 개발 안내가 남아 있는 반면 `live/app.js`와 `assessment`에는 최종 제출 경로가 있다. 코드 경로의 존재는 활성화나 실제 DB 적용의 증거가 아니다.
- REQ-A-004 진단 현황의 상태 정의는 기존 DB 계약을 따른다: 해당 단계 `assessments` 행 없음 = 미시작, `status='draft'` = 작성 중, `status='submitted'` = 제출 완료. 그 밖의 상태값이나 같은 참여자·단계의 중복 행이 있으면 집계하지 않고 오류를 반환한다. 사전 완료율의 분모는 관리자 조직의 등록 참여자 전체로 화면에 명시했다. 요구사항 10절 7번의 완료율 분모 상세 정의가 확정되면 이 기준을 다시 확인해야 한다. 기업 구분은 등록 시 입력한 `participants.company_name`(빈 값은 "소속기업 미지정")이며 참여자 응답의 소속회사(`reg.careers[0].co`)는 읽지 않는다.
- 단위 구분(STEP 07): `organizations`는 관리자·상담사·참여자가 속한 운영 조직(테넌트)이고 서버 권한 범위의 기준이다. 소속기업은 참여자 등록 시 입력한 `participants.company_name` 문자열이며 별도 테이블·ID가 없다. 운영 관리 화면은 두 단위를 따로 표시한다. 같은 기업이 표기만 다르게 입력되면(띄어쓰기 등) 다른 기업으로 집계된다. 앞뒤 공백만 제거한다.
- 담당 상담사가 이 조직의 상담사 목록에 없는 참여자(다른 조직 계정이나 역할이 바뀐 계정을 가리키는 경우)는 "담당 확인 필요"로 따로 세고, 가리키는 계정의 정보는 반환하지 않는다. 기존 상담사 화면은 `counselor_user_id`로 담당을 판단하므로 이 상태의 참여자를 다룰 정책(재배정 등)은 미확정이다.
- 통합 분석 4·5·6번 화면(STEP 11)과 레거시 `rp4`·`rp5`·`rp6`의 대응: (1) 레거시는 만족도 응답이 있는 참여자(`sv`)를 그대로 쓰지만, 서버는 4~6번 화면에 필요한 필드(사전 기대 `expect.d32~d35`, 사후 `sat`의 `q3a`·`q3b`·`q3c`·`q5fit`와 `d32~d35`)가 모두 유효한 응답자만 넣고 나머지는 화면에 제외 인원으로 밝힌다(`detailN`). 제출된 정상 데이터에서는 `satN`과 같다. 유효 기준은 서버 저장 단계의 기존 검사와 같다(사전은 보기 목록 안의 서로 다른 값을 정해진 개수만큼, 사후는 서로 다른 보기 값 1개 이상·`LIM` 이하이고 d33은 3개). (2) **비율의 분모**: 레거시 TOP 목록의 비율은 선택 건수 ÷ 전체 선택 건수이며 참여자 비율이 아니다. 이를 그대로 유지하고 화면에 분모를 적었다(비율을 100%로 맞추거나 참여자 기준으로 바꾸지 않았다). 단일 선택 문항(마음 상태 Q3.1, 컨설팅 기대·도움 Q5.0)은 사전·사후 각각 합계가 기준 인원과 같다. (3) **순위 기준이 문항마다 다르다**: Q4.0과 Q5.0은 사전 선택 수, Q6.0은 사후(극복) 선택 수 기준 TOP3이며 레거시 그대로 보존했다. 동점은 보기 순서가 먼저다. (4) 사전 선택이 0건인 보기의 변화율은 0이다(레거시 규칙). (5) 질문마다 의미가 달라(기대·도움·충족도·장애요인) 합치거나 같은 지표로 비교하지 않고 각각 따로 표시한다. 레거시 화면 문구(예: Q4 각주의 "3가지 우선순위")도 그대로 두었다. (6) **숫자 문자열 응답**: 만족도 점수(예: `q3a`)가 문자열이면 서버는 4~6번 모집단에서 제외하지만 레거시는 포함하고 평균이 문자열 이어붙이기로 깨진다(테스트로 확인, 보존 특이점 6과 같은 원인, 고치지 않음). (7) 보기 목록과 차트 라벨은 서버가 응답에 포함하며(승인된 표시용 문구) 레거시 `OPT`·`SH`와 같음을 테스트로 확인했다. 읽는 응답 필드는 위 경로뿐이며 `d36`·`q7`·자유 의견은 읽지 않는다.
- 통합 분석 2·3번 화면(STEP 10)과 레거시 `rp2`·`rp3`의 대응: (1) 요인은 진단 문항 1개이며 요인 순위는 1~15위 전체를 반환하고 레거시처럼 화면에서 상위 5개만 강조한다(영역은 1~5위, 상위 3개 강조). 동점은 레거시와 같이 표의 앞쪽이 먼저다. (2) 만족도 모집단은 레거시 `sv`(`p.sat`가 있는 사전·사후 참여자)에 대응하지만, 레거시는 만족도를 한 문항만 답해도(`setSat`가 객체를 만든다) 포함하는 반면 서버는 Q1·Q2가 모두 1~5의 정수일 때만 포함하고 나머지는 화면 3에서 제외한다(제출된 사후 응답은 서버가 만족도 완전성을 검사하므로 정상 데이터에서는 차이가 없다). Q1과 Q2는 함께 필수라 두 항목의 분모가 항상 같으며 화면에 분모를 적었다. (3) **숫자 문자열 응답**: 레거시 `full`은 '3'을 통과시키지만 영역 합이 문자열 이어붙이기가 되어 평균이 깨지고(보존 특이점 6), 만족도 점수가 문자열이면 `===` 비교로 분포에서 빠져 합이 인원과 맞지 않는다. 서버는 정수만 모집단에 넣으므로 2·3번 화면에는 영향이 없고, 해당 참여자는 제외 인원(두 진단) 또는 만족도 제외(만족도)로 센다. 같은 데이터를 레거시 화면에 넣으면 모집단과 수치가 달라진다(테스트로 확인). 레거시와 보존 규칙은 고치지 않았다. 만족도 조회는 `answers->sat->q1`·`q2` 두 점수만 읽으며 선택형 응답·자유 의견은 읽지 않는다.
- 통합 분석(STEP 09)과 레거시 `aReport`의 대응: 레거시에는 사후 "제출" 상태가 없어 사후 15문항이 채워진 참여자(`full(post)`)를 넣지만, 운영 기준은 사후 **최종 제출**이다. 레거시 `full`은 문자열 '3'도 통과시키지만(보존 특이점 6) 서버 모집단은 정수만 인정하고, 두 진단을 제출했지만 응답이 불완전한 참여자는 제외 인원으로 따로 표시한다. 기업 선택은 레거시 `ENT` 이름 대신 등록 소속기업(`company_name`)이며 소속기업 미지정 참여자는 "전체"에만 포함된다. 영역 차이와 1~5위는 레거시 `rp2` 영역 종합 열의 식이고, `rp1`은 1~3위만 표시한다. 변화율·합계는 레거시처럼 반올림된 평균으로 계산한다. 사전 평균 0일 때 변화율 0은 레거시 규칙이지만 원점수 최소값이 3이라 실제로는 생기지 않는다. 0명이면 레거시처럼 수치 없이 안내만 표시한다.
- 관리자 보고서(STEP 08)는 상담사 보고서와 인쇄되는 쪽(`section.sheet`)이 같다. 인쇄되지 않는 도구 영역만 다르다: 돌아가기 버튼이 관리자 목록으로 가고, 상담사 변경 이력 패널(과거 응답 문구 포함)은 관리자에게 넣지 않으며, 서버 공용 렌더러가 넣는 "응답 수정 (상담사)" 버튼은 관리자 화면에서 제거한다(수정은 상담사 전용). 운영 관리 목록은 보고서 요청용으로 참여자 ID를 반환하며 이 ID는 조회 키일 뿐 권한 근거가 아니다.
- README의 과거 비공개 저장소 설명은 `decisions.md`의 공개 유지 결정과 다르다. 본 점검에서 공개 범위를 변경하거나 원격 공개 설정을 확인하지 않았다.

## 11. 미검증 항목 및 운영 위험

- **STEP 14-A 고객사 마스터 미적용 조건**: Supabase CLI와 로컬 Postgres/Docker가 준비되어 있지 않아 `supabase/proposals/client-companies.sql`로 작성했다. 적용 완료 마이그레이션 이력을 만들지 않았다. ## 12. 구현 우선순위 및 다음 작업

1. **P0**: 인증·담당/조직 범위·RLS와 직접 DB/RPC 우회, 서버 계산·데이터 최소화, 감사 및 실환경 검증 계획을 확정한다. 실데이터 베타 전 보안·회귀와 사용자 승인이 필요하다.

이는 우선순위 제안이며 후속 코드 변경이나 일정의 승인이 아니다. 개인별 비교 화면은 정책 결정 전 임의 삭제·권한 전환하지 않는다.

### 미검증·승인 조건·위험

실제 DB catalog·RPC·RLS·유일 키·FK·Auth hooks·운영 환경은 확인하지 않았다. SQL을 실행하거나 실제 계정을 만들지 않았다. SQL 실행·권한·직접 테이블/RPC 접근·실제 Auth 로그인과 비밀번호 변경은 검증 전이다. `counselor-registration.md`의 검토 조건과 비운영 연동 검증, 사용자 별도 DB/Auth·배포 승인을 완료하기 전 발급 플래그를 켜면 안 된다. 신규 표·RPC 적용과 기존 직접 접근 경로의 상담사 비밀번호 변경 gate 검증이 필수다.

중간 실패·네트워크 오류·클라이언트 응답 유실은 예약을 유지하며 자동 삭제·자동 재발급하지 않는다. 비밀번호는 성공 응답에서 한 번만 제공하고 화면 메모리에만 보관한다. 로그아웃·화면 분리·pagehide 때 제거한다. 비밀번호 유실·pending 예약 해결·관리자 비밀번호 초기화 UI는 이번 범위에 없어 수동 확인이 필요하다. 상담사 정지·기존 내담자 재배정도 제외했다. 공통 account/등록 guard 변경과 기존 담당자 테스트 불일치가 회귀 검토 지점이다. 운영 배포 준비 완료로 판정하지 않는다.
