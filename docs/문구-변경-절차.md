# 코멘트·키워드 문구 변경 절차

기획자가 결과 보고서의 **코멘트**나 **인생키워드** 문구를 바꿀 때의 절차다. 아래 "확인한 사실"은 실제로 복사본에서 문구를 바꿔 테스트를 돌려 얻은 결과이고, 확인하지 못한 것은 맨 아래에 따로 적었다.

## 1. 한눈에 보기
- 문구는 `src/data/feedback-comments.js`(코멘트 15개)와 `src/data/feedback-keywords.js`(키워드 42개 + 분류표)에만 있다. 이 두 파일의 **문구 글자만** 바꾼다.
- 바꾸면 안 되는 것: 코드(`Code_A_01`, `A_20_01` 등), 항목 개수, 항목 순서, `GOAL_TO_KW`. 이것들은 문구가 아니라 계산 규칙·연동 값이다(별도 승인, 6장).
- 정답표(`tests/golden`, `tests/contract`, `tests/snapshot`)는 **승인 없이 고치지 않는다.** 문구를 바꾸면 일부 정답표가 의도적으로 바뀐다(3장). 개발자가 바뀐 목록이 3장과 같은지 확인하고, 승인을 받은 뒤 정답표를 갱신하고 커밋한다.

> **기획자 주의 — 이미 발행한 보고서와 문구가 달라질 수 있습니다.**
> - **코멘트**를 고치면, 이미 제출된 응답의 보고서도 **다시 출력할 때 새 문구로 바뀝니다.** 지면으로 이미 드린 보고서와 다시 뽑은 보고서의 코멘트가 서로 달라질 수 있습니다.
> - **키워드**는 제출한 시점의 문구가 저장되어 있어 고쳐도 이미 제출된 응답은 **바뀌지 않습니다.** 새로 제출하는 응답부터 새 문구가 나옵니다.
> - 따라서 코멘트 문구를 바꾸기 전에, 이미 발행한 보고서를 다시 출력할 일이 있는지 확인해 주세요. 어느 쪽으로 통일할지(과거 응답도 새 문구로 / 제출 당시 문구 유지)는 아직 정해지지 않았습니다(`docs/decisions.md` 별도 판단 9번).

## 2. 문구가 보고서에 반영되는 방식 (확인한 사실)
| 대상 | 저장되는 것 | 이미 제출된 응답의 보고서 |
|---|---|---|
| 코멘트 | 코드만(`result.comment`, 예 `Code_A_01`) | **새 문구로 바뀐다.** 보고서를 열 때마다 현재 `CMT`에서 읽는다. |
| 키워드 | 코드와 **문구 사본**(`result.kw.age/goal/pro.text`) | **옛 문구가 그대로 남는다.** 새 문구는 앞으로 제출하거나 다시 뽑는 응답에만 적용된다. |

- 확인 방법: `KW_PRO`의 한 문구를 바꾼 복사본에서 옛 문구가 저장된 참여자의 보고서를 열었더니 옛 문구가 그대로 보였다. 코멘트 오탈자를 고친 복사본에서는 같은 코멘트 코드를 가진 참여자의 보고서 본문이 새 문구로 바뀌었다(스냅샷 8화면이 달라진 것으로도 확인).
- 그래서 "이미 나간 보고서의 키워드 문구도 바꿔 달라"는 요청은 이 절차로 되지 않는다. 별도 데이터 보정이 필요하며, 이 문서의 범위 밖이다.

## 3. 문구를 한 글자 바꾸면 어떤 정답표가 바뀌는가 (변조 시험 결과)
복사본에서 아래처럼 바꾸고 `골든 + contract + 스냅샷 + e2e`(106건)를 돌렸다. 표의 "바뀐다"는 **의도적으로 바뀌는 정답표**(갱신 대상)이고, 이 밖에 실패가 나오면 문구 변경이 아닌 다른 문제다.

| 변경(시험한 것) | 바뀌는 정답표 | 바뀌는 화면 기준선 |
|---|---|---|
| **코멘트** 본문 한 글자(`Code_A_01`의 `어렵워지게`→`어려워지게`) | `tests/contract/data/`의 `comments.json`, `feedback-data.json`, `assessments.json.gz`(연동 JSON의 코멘트 문구), `manifest.json` | 결과 보고서 8화면의 HTML·JSON(내담자용·상담사용 × `hong`·`star`·`post`·`max`), 캡처 3화면(`res-p-hong`, `res-c-hong`, `res-p-star` × 6장, 로컬) |
| **연령대 키워드** 문구 한 글자(`KW_AGE` 20대 `A_20_01`) | `tests/golden/data/compute-result.json.gz`, `tests/contract/data/feedback-data.json`, 각 `manifest.json` | 없음 |
| **인생키워드(공통)** 문구 한 글자(`KW_PRO` `C_10_01`) | `tests/golden/data/compute-result.json.gz`, `tests/contract/data/feedback-data.json`, `assessments.json.gz`, 각 `manifest.json` | 없음 |
| **경력목표 키워드** 문구 한 글자(`KW_GOAL` 창업 `B_30_01`) | 위와 같음 | 없음 |

- **어느 화면 기준선이 바뀌는지는 시작 데이터(`tests/snapshot/fixture.json`)에 달려 있다.** 이 데이터의 보고서가 그 코멘트·키워드를 보여 줄 때만 화면 기준선이 바뀐다. 그래서 키워드 3가지 시험에서는 화면 기준선이 바뀌지 않았다. 바뀌지 않았다고 해서 문구가 검증되지 않은 것은 아니다. 문구 자체는 `feedback-data.json`과 `compute-result.json.gz`가 모두 덮는다.
- e2e는 문구를 확인하지 않아 어떤 경우에도 바뀌지 않았다.

## 4. 문구 변경으로 바뀌면 안 되는 정답표 (확인한 사실)
위 시험 4가지에서 아래 정답표는 **한 건도 바뀌지 않았다.** 문구 변경 뒤 이 중 하나라도 실패하면 문구가 아닌 것을 건드린 것이므로 중단하고 보고한다.
- 환산·판정: `golden/conversion.json`
- 코멘트 대상 영역 선택(최저 원점수, 동점 시 A>B>C>D>E): `golden/comment-area.json.gz`
- 키워드 선택 규칙(무작위 선택 호출 순서·개수)과 연령대·13번 분류: `golden/boundaries.json`, 그리고 `golden/compute-result.json.gz`의 호출 순서(`pickSeq`)와 선택된 코드·분류. 키워드 문구를 바꾼 3가지 복사본에서 `computeResult` 47,520건을 비교하니 호출 순서는 모두 같았고, **코드·분류가 달라진 건은 0건**이었다. 달라진 것은 문구뿐이었다(20대 키워드 1개 변경 시 2,970건, 공통 키워드 1개 변경 시 5,280건, 창업 키워드 1개 변경 시 2,160건). 코멘트 문구를 바꾼 경우는 `computeResult` 정답표가 코드만 담고 있어 0건이다.
- 상담사 수정 재계산(`recomputeResult` 유지 규칙)과 결과 재생성 조건: `golden/recompute.json.gz`, `golden/counselor-edit.json`, `golden/result-of.json`
- 자체 검증 탭 57건: `golden/self-tests.json`
- 인쇄 쪽수(내담자용 3쪽·상담사용 5쪽), CSS 지문, 문항 정의·`missing`·`ansText`·시드·`globals.json`

## 5. 절차 (개발자)
1. **요청 받기**: 기획자가 바꿀 항목을 "파일 / 코드 / 변경 전 문구 / 변경 후 문구 / 이유" 표로 보낸다. 코드·개수·순서·`GOAL_TO_KW` 변경이 섞여 있으면 6장으로 보낸다.
2. **문구 수정**: `src/data/feedback-*.js`에서 요청한 문구의 글자만 바꾼다. 따옴표·쉼표·코드·순서는 건드리지 않는다. `git diff -- src/data`로 의도한 줄만 바뀌었는지 확인한다.
3. **실패 목록 점검**: `npm run test:src`를 실행한다. 실패한 테스트가 3장 표의 해당 줄과 같아야 한다. 4장 목록이 실패하거나 3장에 없는 실패가 있으면 중단하고 보고한다.
4. **정답표 갱신 준비**(승인 전에 미리 만들어 diff를 보고하기 위한 단계):
   ```powershell
   $env:GEN_APPROVED = "문구 변경 <요청 번호·날짜>"
   $env:GEN_TARGET = "src/index.html"
   node tests/golden/generate.mjs        # 키워드 문구를 바꾼 경우 compute-result 가 바뀜
   node tests/contract/generate.mjs
   node tests/snapshot/update.mjs --target src/index.html
   Remove-Item Env:GEN_TARGET, Env:GEN_APPROVED
   ```
   `GEN_APPROVED`가 없으면 도구가 거부한다(오라클 보호). 캡처 이미지(저장소 밖 로컬 기준)는 `node tests/snapshot/update.mjs --visual --target src/index.html`(같은 환경 변수 필요).
5. **바뀐 정답표 확인**: `git diff --stat -- tests/golden tests/contract tests/snapshot`가 3장 표와 같은 파일만 보여야 한다. 다르면 `git checkout -- tests`로 되돌리고 보고한다.
6. **재검증**: `npm run test:src`와 `$env:TARGET_HTML='src/index.html'; npm run test:visual`이 모두 통과해야 한다.
7. **승인 요청**(아래 7장) → 승인 후 문구 파일과 정답표를 **같은 커밋**으로 커밋한다. 커밋 메시지는 `문구 변경(승인): <요청 번호·날짜> — <바뀐 항목>`으로 쓰고, 아래 8장 이력 표에 한 줄 추가한다.

> 승인 후에는 `legacy`와 작업본의 문구가 달라진다. 그러면 legacy를 대상으로 하는 `npm test`는 위 3장의 정답표 때문에 실패하는 것이 정상이다. 이후 기본 검증은 `npm run test:src`다. legacy 파일 자체는 계속 수정하지 않는다.

## 6. 문구가 아닌 변경 (별도 승인 필요, 문구 절차로 처리하지 않는다)
| 변경 | 시험에서 확인한 영향 |
|---|---|
| `GOAL_TO_KW` 분류표 변경(13번 보기 → 키워드 그룹) | 골든 7개(환산·판정, `computeResult`, 연령대·13번 분류, 상담사 재계산, `resultOf`, 자체 검증, 내용 일치)와 contract 3개, 자체 검증 화면이 바뀐다. 분류 규칙 변경이므로 계산 로직 변경으로 본다. |
| 항목 삭제·추가(예: 20대 키워드를 3개에서 2개로) | `computeResult` 전수와 상담사 재계산 정답표, `feedback-data.json`이 달라진다. 엔진이 `pick(3)`·`pick(9)`로 고정 개수에서 고르므로 개수를 바꾸면 계산 로직 변경이다. |
| 코멘트·키워드 코드 변경, 항목 순서 변경 | 시험하지 않았다. 코드는 저장된 결과와 연동 JSON(`feedbackCode`, `keywordCodes`)에 들어가므로 계약 변경으로 보고 별도 승인한다. |

## 7. 승인 방법
승인권자에게 아래를 한 번에 보고하고 "승인"이라는 답을 받은 뒤에만 커밋한다(승인 전에는 정답표 변경을 커밋하지 않는다).
1. 변경 전·후 문구 표(요청한 그대로)
2. `git diff --stat -- tests/golden tests/contract tests/snapshot` 결과와, 이것이 3장 표와 같다는 확인
3. `npm run test:src`·`test:visual` 통과 건수
4. 이미 제출된 응답에 미치는 영향(2장): 코멘트는 소급되고 키워드는 새 응답부터

|---|---|---|---|---|---|

## 9. 확인하지 못한 것
- 코멘트·키워드의 **코드**나 **순서**를 바꿨을 때의 영향(6장 마지막 줄).
- 문구 길이를 크게 바꿔 인쇄 쪽수가 3쪽·5쪽에서 달라지는 경우. 쪽수 테스트가 잡도록 되어 있으나 실제로 늘려서 시험하지는 않았다.
- 글꼴이 다른 PC에서의 캡처 비교(캡처는 이 PC의 글꼴에 묶여 있다. 글꼴은 단계 4에서 고정한다).
- 위 시험은 현재 시작 데이터 기준이다. 다른 코멘트·키워드는 다른 화면 기준선에 나타날 수 있다.
