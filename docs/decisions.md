# 결정 기록

## 확정
1. 서비스 정책: 내담자는 자신의 결과를 직접 볼 수 없다. 상담에 참여해야 상담사로부터 지면으로 받는다(상담 참여 유도).
2. 기준 파일: 통합본(본부장님 아티팩트 복사본에 원본 엔진을 반영한 것). 본부장님은 새 프로토타입을 추가로 주지 않는다.
3. 사용자 응답 계산 로직은 리팩토링 중 바꾸지 않는다.
4. 화면은 현재의 문자열 템플릿 방식을 유지한다. 디자인을 유지한다.
5. 폰트는 모든 환경에서 같은 모양으로 고정하되, 기획자 요구로 나중에 바꿀 수 있게 폰트 설정을 한 곳에 둔다.
6. 참여자·상담사·관리자·고객사 담당자는 서로 다른 URL로 진입한다. 확정된 것은 "역할별 분리"이며 경로 이름은 제안이다: `/`(참여자), `/counselor`, `/admin`, `/manager`.
7. 계정: 상담사와 고객사 담당자의 아이디·비밀번호는 관리자 페이지에서 부여한다. 참여자는 상담사·관리자가 등록한다(현재 방식: 연락처 끝 8자리 아이디, 6자리 비밀번호).
8. 같은 규칙·정의는 한 곳에 두고 여러 코드가 공유한다. 계산 로직이나 상담사·관리자 연동부가 나중에 바뀌어도 한 곳만 고치면 되게 한다.
9. 작업 환경은 VS Code의 Claude Code이다.
10. 스택: 프런트는 Vite 멀티페이지(화면은 현재의 문자열 템플릿 유지), 백엔드는 Supabase(로그인, 데이터베이스, 서버 함수). 이전의 미결정 항목(Vite + Supabase 또는 Next.js)을 이 결정으로 닫는다.
11. 제약(서버 함수에서 재사용하기 위함): 엔진(`computeResult` 등 계산), 문항 정의(`QUESTION_DEFS`), 문구 데이터(`CMT`·`KW_*`) 모듈은 화면·`window`·`document`·`localStorage`에 의존하지 않아야 한다. 단계 3의 코드 분할과 단계 7의 서버 이전은 이 제약을 지키는지 검사한다.

## 미결정
- 규칙이 바뀐 뒤 이미 제출된 응답의 판정: 제출 당시 규칙으로 고정(권장) 또는 새 규칙으로 재계산.
- 참여자 초대 링크와 로그인 방식(현재 `#join-아이디` + 연락처·6자리 비밀번호), 로그인 시도 제한.
- 개인정보 수집·이용 고지문과 보관 기간.
- 관리자 계정 추가 허용 여부, 최초 로그인 시 비밀번호 변경 강제 여부, 상담사 삭제·정지 시 담당 내담자 재배정 방식, 상담코드와 로그인 아이디의 분리 여부.

## 현재 코드에서 확인한 구조적 사실 (게시본 기준, 코드를 읽고 측정)
- 판정 규칙이 세 형태로 공존한다: `GRADE_SETS`(화면이 사용), `level()`, `labelRaw()`. 뒤의 둘은 자체 검증에서만 쓰인다.
- 환산식이 세 곳, 문항 수 15가 아홉 곳, 문항 코드 나열이 여섯 곳, 보기 목록 `OPT['…']` 직접 참조가 34곳이다.
- 화면 함수 안에서 결과를 만들고 저장한다(`resultOf`가 `save()`를 호출, `vResult`에서 호출).
- 응답을 보기 문구 텍스트로 저장한다(`computeResult`가 `OPT['goal.b13'].indexOf` 사용).
- 기업 연결이 이름 문자열이다(`entOf`).
- 비밀번호가 평문이고, 역할 전환은 버튼, 상담사 선택은 드롭다운이다. 고객사 대시보드도 브라우저가 전체 응답을 읽어 집계한다.
- 폰트 `Pretendard`를 지정했지만 폰트 파일을 포함하거나 불러오지 않는다.
- 인쇄 축소(`fitSheets`)가 733×1000 고정값에 의존한다. 표지 이미지는 CSS 안에 base64 약 91KB로 내장돼 있다.

## 리팩토링 후 별도 판단 (지금은 고치지 않는다. 정답표에 현재 동작이 기록돼 있다)
리팩토링 중에는 보존하고, 단계 8 이후 기획 판단으로 바꿀지 정한다.
1. 상담사 수정 시 13번 1순위 분류만 바뀌어 키워드가 새로 뽑혀도 변경 이력의 `resultChanged`는 false다(`applyCounselorEdit`가 코멘트 코드와 원점수만 비교한다). 정답표: `counselor-edit.json`.
2. 상담사 수정으로 생년월일(`birthDate`)만 바뀌고 출생연도(`birth`) 필드가 그대로면 연령대 키워드는 다시 계산되지 않는다(`computeResult`는 `birth`만 읽는다). 화면(`setBirth`)은 두 값을 함께 바꾸지만, 계산 함수 쪽은 단계 0에서 그 연결을 확인하지 않았다. 정답표: `counselor-edit.json`.
3. 결과(`result`)는 `resKey`(원점수 15개 · 출생연도 · 13번 1순위 · 응답연도)가 달라질 때만 다시 뽑는다. 13번 2순위, 같은 해의 응답일, 이름, 상담사, 사후 응답은 키에 없다. 정답표: `result-of.json`.
4. 응답일(`preDate`)이 없는 응답은 연령 계산에 실행 시점의 연도(`today()`)를 쓴다. 같은 응답이라도 연도가 바뀌면 연령대 키워드가 달라질 수 있다. 정답표 생성은 시계를 고정해 이를 피한다(`npm run golden:clockdiff`로 영향 항목 확인).
5. 화면용 보기 문구(`QLABEL`)와 보고서용 보기 문구(`OPT`)가 8개 문항 14개 보기에서 다르다(상세는 위 "원본(엑셀)과 맞춰 확인할 사항"). 문구를 하나로 맞출지는 별도 판단이다. 단계 2b에서도 두 문구는 합치지 않고 문항마다 두 필드로 유지한다. 정답표: `question-defs.json`의 `options.screen`·`options.report`.
6. 진단 응답 값 검사(`missing`, `full`)가 `v>=1&&v<=5`라서 문자열 '3'도 완료로 인정한다(2a 정답표 `missing.json`). 문자열이 섞였을 때 합계(`sum`)가 어떻게 되는지는 확인하지 않았다.
7. 업종·기대소득에서 '기타'를 고른 뒤 내용을 비우면 `ansText`가 `기타 ()`를 돌려준다(`anstext.json.gz`). 제출 검증(`missing`)은 이 상태를 막지만 작성 중 데이터와 상담사 수정 경로에서는 나올 수 있다.
8. `toAssessment`에서 B15(달성 가능성)가 빈 값이면 0이 된다(`+''`). 빈 값과 실제 0을 구분할 수 없다. B16이 숫자가 아니면 `NaN`이 JSON에서 `null`이 된다(`assessments.json.gz`의 "달성가능성 빈 값·소요 abc"). 제출 검증이 막는 값이라 작성 중 데이터에서만 나온다.
9. **문구 수정 뒤 재출력 불일치(정책 결정 필요)**: 코멘트는 코드만 저장되어 문구를 고치면 이미 제출된 응답의 보고서도 다시 출력할 때 새 문구로 바뀐다. 키워드는 제출 시점의 문구가 결과에 저장되어 있어 고쳐도 바뀌지 않는다. 지면으로 이미 발행한 보고서를 나중에 다시 출력하면 코멘트 문구가 발행본과 달라질 수 있다. 문구를 제출 시점으로 고정할지(코멘트도 사본 저장), 항상 최신으로 소급할지(키워드도 새로 읽기) 정해야 한다. 지금은 현재 동작을 그대로 두며, 근거는 `docs/문구-변경-절차.md` 2장이다.
10. **정답표 생성기의 승인 사유 변수(`GEN_APPROVED`)는 통제가 아니라 마찰이다**: 아무 문자열이나 넣으면 통과하므로 오조작을 줄일 뿐 승인을 증명하지 못한다. 실제 통제는 갱신된 정답표 diff(`git diff --stat`와 변경 내용)를 사람이 검토하고 승인하는 것이다. 절차 문서도 이 전제로 쓰여 있다.
11. **고객사 담당자 접속 링크 정책(#client)**: 지금 `mgrMsg`가 만드는 안내 링크는 `…#client`이고, 앱이 해시를 읽어 고객사 화면으로 전환한다. 단계 3에서 진입점이 `/manager/`로 분리돼도 `mgrMsg`의 문구는 바꾸지 않는다. 새 구조에서 `#client` 링크가 어떻게 동작하게 할지(예: `/`에서 `#client`이면 `/manager/`로 이동)는 3c 설계에서 보고하고, 새 링크 정책(문구·기존에 보낸 링크의 호환)은 별도 판단이다.

## 단계 1b 이후 남은 중복 (다음 단계에서 정리하거나 판단)
1b에서 `src/js/02-eval-config.js`에 문항·영역 구조(`AREA_COUNT`, `ITEMS_PER_AREA`, `SCALE_MIN/MAX`, `ITEM_COUNT`, `RAW_MIN/MAX`), 환산 함수 `toScore`, 차트 눈금(`GRADE_TICKS`, `BAL_Y_TICKS`, `BAL_Y_LEVELS`)을 두었다. 환산식은 `toScore` 하나이고 `level()`·`labelRaw()`는 제거했다. 아래는 일부러 남긴 것이다.
1. **PPT 내보내기 코드의 숫자**(승인에 따라 이번 범위 제외): `valAxisMaxVal:15`, 문구 "영역별 원점수(15점 만점)"·"영역 종합(15점)", `Math.floor(i/3)`. PPT는 아티팩트 전용 기능이라 호출 기록 기준선이 없어 변경해도 검증할 수 없다.
2. **영역당 문항 수 3의 암묵적 사용**(`ITEMS_PER_AREA` 미사용): `[0,1,2].map(j=>…)`·`ai*3+j`(설문 15문항 화면, 사후 진단 화면, 결과 보고서 3쪽의 세부 항목, 사전사후 상세 표), `Math.floor(i/3)`·`i%3`·`i/3`(요인→영역 대응), 시드 데모 데이터(`j*3`, `i%5` 등). 계산이 아니라 화면 배치와 데모 데이터이며, 단계 2의 문항 정의 일원화에서 함께 정리한다.
3. **5점 척도 상한의 표시용 사용**: 결과 보고서 3쪽의 막대 폭 `v/5*100`, 만족도 카드의 `avg/5`. `SCALE_MAX`로 바꿀 수 있으나 이번 범위(환산식·문항 수·차트 눈금)에 넣지 않았다.
4. **차트 눈금은 계산하지 않고 같은 값으로 옮겼다**: `GRADE_TICKS`(33.3·58.3·83.3)는 지금 판정표(`conv`)의 구간과 같아 보이지만 판정 세트를 바꾸면 달라지는 별도 판단이다. `BAL_Y_LEVELS`(91·70·45·17)는 구간 중앙값(91.7·70.8·45.8·16.7)과 달라 계산으로 바꾸면 위치가 변한다(디자인).
5. **자체 검증 탭(A안)**: 문구는 그대로 두었다. '평가기준 C22:E34' 13개 항목의 기대값은 엑셀 표를 옮긴 고정 값(`C22E34`)이고 계산값은 `gradeOf`다. 이전에는 옛 규칙 `labelRaw`와 `level`을 서로 비교했으나 지금은 `gradeOf`와 엑셀 표를 비교한다. `C22E34`는 `labelRaw`의 구간을 옮겨 적은 것이라, 원본 엑셀 값과 대조한 것은 아니다.

## 단계 2b 이후 남은 중복 (정의에 있는 값을 쓰지 않고 따로 적은 곳)
2b에서 `src/js/00-question-defs.js`(`QUESTION_DEFS`, `QUESTION_STEPS`)를 단일 원본으로 만들고, 아래 9개 전역을 원래 자리에서 값만 파생했다: `QT`, `REQUIRED`, `C_CODES`, `WSTEPS`, `QLABEL`, `FACTORS`, `SH`, `LIM`(문항 9개 경로), `OPT`(문항 11개 경로). 호출 지점은 바꾸지 않았다. 아래는 정의가 있는데도 따로 적혀 있는 곳이다.
1. **`missing()`의 선택 개수·범위 상수**: B13 정확히 2(서로 다름), D33 정확히 3(서로 다름), D35 정확히 2, D36 1~2, D32·D34·B11·B12·B14 최소 1, B15 `\d{1,3}`·100 이하, B16 `\d{1,3}`·600 이하, 생년월일 1900년 이상. 정의의 `max`(= `LIM`)와 따로 적혀 있다. 정의에는 최소 개수와 범위가 아직 없다.

5. **`QT[`·`QLABEL[`·`qLabel(`·`LIM[`·`WSTEPS`·`C_CODES` 호출**: 각각 2·4·3·2·7·5곳. 이름은 그대로 두었다.

10. **차트 라벨의 보기 수**와 보기 목록 길이가 같아야 한다는 조건은 자체 검증 탭에 있고, 정의에도 점검이 있다(`defs.spec.mjs`). 두 곳에서 따로 확인한다.
11. **정의의 `area` 필드와 위치 계산**: 진단 문항이 어느 영역에 속하는지는 정의에 `area`(0~4)로 있지만, 채점과 화면은 이 값을 읽지 않고 문항 순서로 다시 계산한다. `rawSums`·`areaScores`·`rawA`의 `slice(i*ITEMS_PER_AREA,(i+1)*ITEMS_PER_AREA)`, 설문 화면·결과 3쪽·사전사후 상세의 `[0,1,2].forEach`와 `ai*3+j`, `Math.floor(i/3)`·`i%3`·`i/3`(요인→영역 대응)이다. 정의의 순서·`area`·`factor`와 이 위치 계산이 어긋나지 않는지는 `tests/contract/defs.spec.mjs`의 "영역당 3문항 묶음" 테스트가 검사한다(문항을 재배열하면 이 테스트와 채점 정답표가 함께 실패한다). 위치 계산을 `area` 조회로 바꾸는 것은 계산 로직 변경에 해당하므로 별도 승인이 필요하다.
12. **파생 전역의 제자리 변경 점검(단계 2b 마무리 확인)**: `OPT`·`LIM`·`WSTEPS`·`C_CODES`·`SH`·`FACTORS`·`QT`·`QLABEL`·`REQUIRED`에 `push`·`sort`·`splice`·`reverse`·`fill` 등을 직접 부르거나 요소를 대입하는 코드는 `src`에 없다(grep 확인). 대입은 `03-options.js`의 `OPT['sat.…']`·`LIM`의 `sat.*` 키 추가와 별칭뿐이다. 파생 뷰는 정의에서 `map`/`filter`로 새로 만든 배열·객체라, 뷰를 바꿔도 `QUESTION_DEFS` 원본은 변하지 않는다. 뷰 안에서 같은 객체를 공유하는 곳은 `OPT['sat.d32'~'d35']`↔`OPT['expect.…']`와 `WSTEPS[3].codes`↔`C_CODES`뿐이며 `globals.json`이 기록한다.
