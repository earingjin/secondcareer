# DEV-009B-2 기존 Supabase 프로젝트 기준 적용 준비

기준 커밋 `1249b91`. **운영 DB 에 접속하지 않았고, 아무 변경도 적용하지 않았다.**
표기: **[확인]** 파일·명령으로 직접 확인 · **[기준선]** 로컬 운영 카탈로그 기준선(2026-11-02 캡처, 비공개)과 대조 · **[미검증]** 실제 운영 DB 확인 필요

## 1. 운영 DB 계약 확인 결과

### 1.1 읽기 전용 접근 가능 여부
- **[확인]** 이 PC 에는 운영 DB 를 읽기 전용으로 조회할 수단이 없다. psql·Supabase CLI 미설치, DB 접속 정보·관리 토큰 없음, Supabase 연동 도구 없음.
- 지시에 따라 우회하지 않았다. **실제 운영 카탈로그는 이번 작업에서 확인하지 못했다.**
- 대신 사람이 실행할 읽기 전용 점검 스크립트를 만들었다: [`supabase/checks/readonly-catalog-check.sql`](../../supabase/checks/readonly-catalog-check.sql)
  - 시스템 카탈로그만 조회하고 고객·응답 행은 읽지 않는다. 사후 행 집계(12번)는 주석 처리했다.
  - `begin transaction read only … rollback` 으로 감싸 쓰기가 불가능하다.
  - 함수 본문은 출력하지 않고 해시만 출력한다. 결과는 기준선 기대값(비공개 파일)과 대조한다.
  - **결과에는 운영 정책·정의 정보가 있으므로 공개 저장소·채팅에 붙이지 않고 로컬 비공개 파일에만 저장한다.**

### 1.2 기준선 대조로 판단한 제안 SQL 호환성 **[기준선]**
| 항목 | 판단 |
|---|---|
| 사용하는 테이블·열(`user_profiles`, `participants`, `assessments`, `assessment_history`) | 모두 존재. `schema_version` 필수 값 제공, `submitted` 일 때 `submitted_at` 필수 CHECK 충족 |
| `(participant_id, phase)` 유일 제약 | 존재. 사후 행은 참여자당 1개 |
| `assessment_history` 기록 | `action` 값 제한 없음, `actor_user_id` 는 Auth 사용자 FK → Edge Function 이 넘기는 Auth 사용자 id 와 일치 |
| 실행 주체 | 두 RPC 는 `SECURITY INVOKER` 로 `service_role` 권한에 의존. 기존 `write_v1` 도 같은 방식으로 운영 중이므로 `service_role` 의 테이블 권한·RLS 우회가 전제됨 (점검 스크립트 10번으로 확인 필요) |
| 잠금 함수 `hashtextextended` | 기존 `write_v1` 이 사용 중 |
| 새 함수 이름 충돌 | 기준선에 없음 (점검 스크립트 5번으로 확인 필요) |
| 트리거 | 사용자 정의 트리거 없음 → `updated_at` 은 함수가 직접 기록 |

## 2. 이번에 수정한 코드·SQL

## 3. R-P1 대응안과 영향 범위
- 권장안: 앱이 쓰지 않는 직접 접근 권한을 최소 권한 원칙에 맞게 축소. 대안: 정책 범위 축소. 세부 SQL·되돌리기 SQL 은 비공개 로컬 파일에 있다.
- 영향 검토 **[확인]**(저장소 코드 기준):
  - 브라우저 앱: Data API 를 직접 호출하지 않는다(Edge Function·Auth 만 사용) → 영향 없음.
  - Edge Function 3종: `service_role` 로 조회 → 영향 없음.
  - 관리자 CLI(`src/admin/account-cli.cjs`): 별도 키로 조직·프로필·로그인 매핑만 다룸 → `assessments` 미사용.
  - 점검 도구 `verify-auth.cjs`: 이미 "직접 조회 거부(401/403)"를 기대 → 계속 통과해야 함.
  - Supabase 대시보드 테이블 편집기: 관리자 역할로 동작 → 영향 없음 **[추론]**.
- **[미검증]** 저장소 밖의 다른 소비자(외부 대시보드·보고 도구)가 로그인 사용자 토큰으로 응용 테이블에 직접 접근하는지.

## 4. 운영 DB 적용 전 필수 조건
1. 점검 스크립트를 운영 프로젝트에서 실행하고, 결과를 비공개 기대값과 대조해 **차이가 모두 설명됨**.
2. 운영에 배포된 Edge Function 소스가 어느 커밋인지 확인(대시보드에서 내려받아 비교). 저장소 `index.ts` 에는 DEV-007B~009B-1 변경이 누적되어 있다.
3. SQL 문법·동작을 운영 밖에서 1회 이상 실행 검증. 별도 클라우드 프로젝트를 만들지 않는다면 **로컬 Supabase(Docker, `supabase start`)** 에 기준선을 적용해 검증하는 방법을 권장한다(비용 없음, 운영 무관).
4. 최신 백업 확인(대시보드 Database → Backups, 요금제에 따라 일일 백업·PITR 여부 확인)과 적용 직전 스키마 덤프(로컬 비공개 보관).
5. 서버 플래그 `SECONDCAREER_POST_DRAFT_ENABLED` 와 `postTestGate` 가 꺼진 상태 유지 확인.
6. 사용자 승인.

## 5. 적용 순서 (승인 후, 플래그가 꺼진 상태에서)
| 단계 | 작업 | 사용자 영향 | 확인 |
|---|---|---|---|
| 1 | `post-draft.sql` 실행 | 없음(호출하는 코드가 아직 없음) | 점검 스크립트 5·6번: 함수 존재, anon·authenticated 실행 불가 |
| 2 | `post-submit.sql` 실행 | 없음 | 같음 |
| 3 | R-P1 권장안 실행(별도 단계) | 앱 영향 없을 것으로 판단 | 점검 스크립트 9번, 앱 로그인·상담사 목록·보고서 조회 수동 확인 |
| 4 | Edge Function 배포 | 플래그가 꺼져 있으면 사후 경로는 503 유지. 사전·보고서 경로는 저장소 코드로 바뀜 | 사전 저장·제출·상담사 보고서 회귀 확인 |
| 5 | 플래그·게이트 켜기 | **이번 범위 아님**, 별도 승인 | — |

- 1·2 를 4 보다 먼저 한다. 새 Edge Function 은 초안 저장에 `secondcareer_post_draft_v1` 을 호출하므로, 함수가 없으면 플래그가 켜졌을 때 초안 저장이 500 이 된다.

## 6. 실패 시 대응
| 상황 | 대응 |
|---|---|
| SQL 실행 중 오류 | 스크립트가 `begin … commit` 이므로 전체 취소된다. 점검 스크립트로 부분 생성이 없는지 확인 |
| 함수 생성 후 문제 발견 | 플래그가 꺼져 있어 호출자가 없다. 아래 되돌리기 실행 |
| R-P1 적용 후 기능 이상 | 비공개 파일의 되돌리기(권한 재부여) 실행 |
| Edge Function 배포 후 회귀 | 직전 배포본으로 재배포 |

되돌리기(새로 만든 함수만 제거, 데이터 변경 없음):
```sql
begin;
drop function if exists public.secondcareer_post_submit_v1(uuid, uuid, jsonb, text);
drop function if exists public.secondcareer_post_draft_v1(uuid, uuid, jsonb, text);
notify pgrst, 'reload schema';
commit;
```
플래그를 켠 뒤에는 사후 데이터·이력이 생기므로 함수 제거만으로는 복구되지 않는다. 그 이후의 복구는 백업 기준으로 별도 계획이 필요하다.

## 7. 로컬 테스트
- 이번 변경은 SQL 제안서와 점검 스크립트뿐이다. SQL 은 로컬 테스트로 실행·파싱되지 않는다(PostgreSQL 파서 의존성을 추가하지 않았다).
- 회귀 확인용으로 전체 테스트를 실행했다(결과는 커밋 보고 참고).
