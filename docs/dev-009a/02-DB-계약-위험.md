# DEV-009A ② DB 계약 차이 및 위험 목록

표기: **[확인]** 파일로 직접 확인 · **[추론]** 코드·문서에서 도출 · **[미검증]** 실제 DB에서 확인 필요
SQL은 하나도 실행하지 않았다. 아래의 "확인"은 코드·로컬 자료를 읽어서 확인했다는 뜻이며 DB 동작 확인이 아니다.

운영 카탈로그 기준선(로컬 `868f8ce`, 비공개)과 대조한 결과는 **존재 여부 수준만** 적는다. 정의 본문·정책·권한 목록은 공개 저장소에 쓰지 않으며, 상세는 로컬 비공개 문서에 있다.

## 2. `supabase/proposals/post-submit.sql` 정적 검토

참고한 공식 문서(2026-11-02 조회):
- [Database Functions](https://supabase.com/docs/guides/database/functions): invoker 권장, definer 사용 시 `search_path` 고정 필수, 기본적으로 모든 역할이 함수를 실행할 수 있으므로 `public`·`anon`·`authenticated` 에서 revoke
- [Database Advisors 0011](https://supabase.com/docs/guides/database/database-advisors?queryGroups=lint&lint=0011_function_search_path_mutable): `search_path` 를 빈 문자열로 고정 권장
- [Postgres Roles](https://supabase.com/docs/guides/database/postgres/roles): `service_role` 은 RLS 를 우회하는 용도
- [Hardening the Data API](https://supabase.com/docs/guides/database/hardening-data-api): public 의 새 객체는 기본 grant 로 Data API 에 노출될 수 있음. 함수에는 RLS 가 적용되지 않고 `execute` 권한만 의미가 있음

### 문제가 아닌 것으로 판단한 항목 (실제 DB 확인 전 **[추론]**)
- `#variable_conflict use_variable` 위치(본문 첫 줄, `declare` 앞)는 문법상 맞다.
- 동시 제출은 사전 행의 `FOR UPDATE` 로 직렬화되고, 두 번째 트랜잭션은 커밋된 사후 행을 보고 멱등 응답을 돌려준다(READ COMMITTED 기준).
- 제출 후 초안 저장은 Edge Function 의 `.eq('status','draft')` 조건으로 0행 갱신 → 409 가 된다.
- 중복 제출 비교는 jsonb 동등 비교(키 순서 무관)다.

## 4. 운영에 적용하면 안 되는 이유
1. `post-submit.sql` 은 R-S1(빈 응답 제출 허용)·R-S2~S4(권한 경계) 문제가 있고, PostgreSQL 에서 한 번도 파싱·실행되지 않았다.
2. R-P1 이 해결되지 않은 상태에서 사후 기능을 켜면 미제출 응답 비노출 원칙(DEV-008)을 DB 수준에서 보장하지 못한다.
3. 원자성·동시성·잠금 동작은 메모리 모의 테스트로만 검증되었다.
4. 운영 배포 함수 코드와 저장소 코드의 일치 여부를 알 수 없다.
5. AGENTS.md 보안 규칙상 단계 7의 보안 검증과 사용자 승인 전에는 실데이터에 쓰지 않는다.
