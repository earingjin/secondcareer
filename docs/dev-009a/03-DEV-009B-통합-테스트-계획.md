# DEV-009A ③ DEV-009B 격리 DB 통합 테스트 계획

이번 단계에서는 계획만 세웠고 **아무것도 실행하지 않았다.** 동시성·잠금·RLS 시험은 실제 PostgreSQL 에서만 하며 메모리 모의 테스트로 대신하지 않는다.

## 0. 시작 조건 (모두 충족해야 시작)
1. 운영과 다른 **빈 Supabase 테스트 프로젝트**가 있고, 사용자가 "테스트 전용"임을 확인했다. 프로젝트 ref 가 운영 ref 와 다른지 대조한다.
2. 접속 정보(프로젝트 ref, 게시 가능 키, service role 키, DB 접속 문자열)는 Git 에 없는 로컬 설정으로만 전달한다. 테스트 도구는 운영 URL·ref 를 만나면 즉시 중단한다(`src/live/config.js` 의 테스트 모드 검사를 재사용).
3. 스키마 적용 원본과 방법이 승인되었다(예: 로컬 `868f8ce` 기준선. 기준선 README 의 적용 전 게이트를 따른다).
4. `post-submit.sql` 은 ②의 R-S1~R-S7 을 반영한 개정본을 별도 승인 후 **테스트 프로젝트에만** 적용한다.
5. Edge Function 3종을 테스트 프로젝트에 배포하고 `SECONDCAREER_POST_DRAFT_ENABLED=true` 는 **테스트 프로젝트에만** 설정한다. 운영 플래그와 `postTestGate` 는 바꾸지 않는다.
6. 가상 계정만 사용한다. 조직 A: 참여자 P1·P2·P3, 상담사 C1(P1·P2 담당)·C2(P3 담당). 조직 B: 상담사 CB, 참여자 PB. 실제 고객 정보·운영 계정은 쓰지 않는다.
7. Supabase CLI 또는 psql 설치(현재 미설치), 실행 시간 예상과 사용자 승인.

## 1. 공통 준비·측정
- 시작 전 모든 사전(`phase='pre'`) 행의 `id, status, answers, result, updated_at, submitted_at` 해시를 저장한다(시나리오 6에서 비교).
- 각 시나리오 뒤 `assessments` 와 `assessment_history` 의 행 수·상태를 조회해 기록한다.
- 응답 본문 로그에는 가상 데이터만 남기고 토큰·키는 마스킹한다.

## 2. 시나리오

### S1. 실제 Auth 로그인 + 본인 사후 초안 저장·복원
1. P1(사전 제출 완료) 로그인 → `GET ?phase=post` 가 `assessment:null`.
2. 15문항 일부 + 만족도 일부로 `post-draft` → 200, `status:'draft'`.
3. 새 세션으로 재로그인 → 같은 응답이 그대로 복원된다(Q4 순서 포함).
4. `post` 만 보내는 이전 형식으로 저장해도 `sat` 이 유지된다.
5. 같은 `expectedUpdatedAt` 으로 두 번 저장 → 하나는 409.
- 확인: `updated_at` 문자열 형식(②의 R-S10)이 왕복 비교에서 어긋나지 않는다.

### S2. 사후 15문항 + 만족도 최종 제출
1. 미완성(문항 누락, Q4 2개, 의견 201자)으로 `post-submit` → 400, DB 행 변화 없음.
2. 완성 응답 + 최신 `expectedUpdatedAt` → 200, `status='submitted'`, `submitted_at` 존재.
3. DB 에서 사후 행이 1개이고, 이력 1건(`action='post-submit'`, 행위자 = P1)인지 확인한다.
4. RPC 를 직접(psql, `service_role`) `answers='{}'` 로 호출하면 거부된다(R-S1 수정 확인).

### S3. 제출 후 수정 차단·중복·동시 제출
1. 제출 후 `post-draft` → 409, 답 변화 없음.
2. 같은 내용 재제출 → 200, 같은 `submittedAt`, 행·이력 증가 없음.
3. 다른 내용 재제출 → 409.
4. **동시성(실제 PostgreSQL):** 새 참여자 P2 에 대해 아래를 병렬 연결 2개 이상으로 실행한다.
   - (a) 같은 내용 `post-submit` 10건 동시 → 모두 200 또는 409, 사후 행 1개, 이력 1건
   - (b) 첫 초안 생성과 제출 동시 → 데이터 손상 없음. 23505 매핑(R-S7) 확인
   - (c) 초안 저장과 제출 동시 → 제출이 이기면 초안은 409
   - (d) 상담사 사전 수정(`write_v1` edit)과 사후 제출 동시 → 교착 없음, 둘 다 일관된 결과(R-S5)

### S4. 타인·타 조직·타 상담사 접근 차단
1. P2 토큰으로 P1 의 사후 조회·저장·제출 → 본인 데이터만 다루거나 거부되고, P1 데이터는 불변.
2. 사전 미제출 P3 의 `post-draft`/`post-submit` → 403.
3. `?compare=P1` 을 C2(같은 조직·비담당), CB(타 조직), P1(참여자)로 호출 → 403.
4. 비밀번호 변경 전 계정 → 403.
5. **Edge Function 을 거치지 않는 경로:** 로컬 비공개 문서 R-P1 의 확인 절차를 수행한다. 미제출 사후 응답이 보이면 "운영 활성화 차단 사유"로 기록한다.
6. anon·authenticated 로 `rpc/secondcareer_post_submit_v1` 호출 → 권한 오류(R-S4).

### S5. 상담사 사전·사후 비교 조회
1. C1 목록에 P1 사후 상태 `submitted` 와 제출일, P2 `draft`, 미시작자 `new` 가 보이고 초안 내용은 응답에 없다.
2. `?compare=P1` 의 영역 점수가 기존 `areaScores()` 로 계산한 값과 같고, 15문항·만족도가 DB 에 저장된 제출 내용과 일치한다.
3. 응답에 이름·전화·초안 등 불필요한 필드가 없다.
4. 서버 플래그를 끄면 503, 목록에 사후 상태가 없다.

### S6. 사전진단 기존 데이터 불변성
- 0단계에서 저장한 사전 행 해시와 S1~S5 이후 값이 같다. 사전 보고서(`?id=`) HTML 이 시작 전과 같다.

## 3. 결과 판정과 보고
- 각 시나리오는 실제 요청·DB 조회 결과로만 통과를 판정한다. 실행하지 못한 항목은 "미실행"으로 적는다.
- 실패한 동시성·권한 항목은 고치지 말고 재현 절차와 함께 보고한다.
- 테스트 프로젝트 정리(계정·데이터 삭제)는 사용자 승인 후에 한다.
- 예상 소요: 환경 준비를 제외하고 시험 실행 약 30~60분(병렬 시험 포함). 실행 전에 다시 승인을 받는다.
