이 문서는 목표 구조와 이행 조건이다. 인증·서버 함수·RLS가 구현되거나 보안 검증을 통과했다는 뜻이 아니다.

## 1. 보안 목표와 비목표

- 모든 웹 역할에 대해 내부 계산식·평가 설정 원본·전체 피드백 데이터가 브라우저에 전달되지 않게 한다. 관리자도 예외가 아니다.
- 응답·결과·관리 정보는 인증된 사용자와 서버가 확인한 소유권·담당 관계·소속·업무 권한에 따라 최소 범위만 제공한다.
- 기존 Excel 매크로 기준 계산, 현재 보존 중인 특이점, 보고서 내용·디자인을 보존한다. 알고리즘 변경을 보안 작업에 섞지 않는다.
- 저장소 공개 여부는 사용자가 결정한다. 공개 상태를 임의 변경하거나 이력을 재작성하지 않는다. 서버 비밀키·서비스 역할 키·실제 계정 비밀번호·실제 개인정보·신규 기밀 데이터는 커밋하지 않는다.
- 난독화·minify·폴더 이동·역할별 URL 분리를 계산 로직 보호 수단으로 삼지 않는다. URL 분리와 화면 숨김은 권한 검증이 아니다.

기술적 한계: 이미 공개 저장소와 그 이력에 포함된 계산 로직·평가 기준·문구는 외부에 노출된 것으로 취급한다. 서버로 옮기거나 번들에서 제거해도 기존 복제본·캐시·추론 가능성을 회수할 수 없다. 공개 유지 결정은 이 잔여 위험을 포함하며, 과거 로직의 비밀성 회복을 보장하지 않는다. 앞으로의 기밀 서버 소스·데이터는 공개 저장소에 추가하지 않고 별도 접근 통제된 저장·배포 경로를 승인받아 사용한다.

사용자에게 실제로 반환한 화면·문구·응답·결과 값은 개발자 도구나 저장·인쇄로 확인할 수 있다. 이를 숨기는 것은 목표가 아니다. 여러 결과를 통한 규칙 추론도 완전히 차단할 수 없으므로 호출 제한·감사와 함께 잔여 위험으로 관리한다.

## 2. 신뢰 경계: 브라우저 / 서버 함수 / 데이터베이스

| 경계 | 책임 | 신뢰하지 않는 것 |
|---|---|---|
| 브라우저 | 승인된 문항·보기 표시, 응답 입력, 허용된 결과 렌더링·인쇄 | 역할 플래그, 상담사 코드, 참가자 ID, 점수·판정·결과, localStorage, 숨겨진 필드 |
| 신뢰 가능한 서버 함수(Supabase 등) | Auth 토큰 검증, 사용자·관계 조회, 작업별 권한 검증, 입력 검증, 계산·저장·조회, 응답 필드 제한 | 클라이언트가 주장하는 소속·담당·관리 권한 및 계산 결과 |
| PostgreSQL / 비공개 데이터 저장소 | 응답·결과·관계·평가 버전·감사 기록 보관, RLS와 최소 권한, 원자적 갱신 | 브라우저의 직접 테이블·RPC 접근 및 임의 소유자 변경 |

흐름은 브라우저 요청 → 서버의 인증·대상 권한 확인 → 서버 전용 계산/조회 → 허용된 데이터 저장·최소 응답이다. 계산 요청과 재조회 모두 권한을 검사한다. 상담사 코드나 참가자 ID는 조회 키일 뿐 권한 증거가 아니다.

외부에 노출된 스키마의 테이블에는 RLS를 적용하고 역할별 소유·담당·소속 조건을 둔다. RLS는 행 제어이므로 열 단위 비공개 정보는 별도 스키마·권한·응답 투영으로 보호한다. 비공개 설정·문구 원본은 브라우저 Data API/RPC/Storage로 읽지 못하게 한다. 뷰·함수·파일 URL 등 우회 경로도 같은 정책을 적용한다. [Supabase RLS 지침](https://supabase.com/docs/guides/database/postgres/row-level-security)

서버 함수의 사용자 인증과 업무 권한 검증은 별개다. 사용자 수정 가능 메타데이터를 권한 근거로 사용하지 않고 서버 관리 관계를 확인한다. 특권 키가 필요한 작업은 범위를 최소화하고, RLS 우회 권한을 쓸 때도 서버가 대상 권한을 명시적으로 검사한다. [서버 함수 인증 지침](https://supabase.com/docs/guides/functions/auth)

## 3. 역할별 권한표

아래는 최대 허용 범위다. 미승인 작업과 범위는 기본 거부한다.

| 역할 | 응답 | 결과·보고서 | 관리 정보·수정 | 계산식·평가 원본·전체 피드백 |
|---|---|---|---|---|
| 참여자(내담자) | 본인 설문 작성·저장·재개·제출. 사후진단·만족도는 담당 상담사 허용 후 참여; 타 참여자 데이터 금지 | 개인 결과보고서 직접 조회·인쇄 금지. 담당 상담사를 통한 결과 안내 | 본인의 허용된 정보만 | 금지 |
| 상담사 | 서버가 확인한 본인 담당 내담자의 업무상 필요한 항목 | 담당 내담자의 개인 결과보고서 조회·인쇄. 통합 분석보고서 생성·조회·인쇄·관리 금지 | 승인된 응답 수정·재계산과 이력 기록, 담당 내담자의 사후진단 허용·안내 | 금지 |
| 관리자 | 서버에서 확인한 조직·업무 권한에 명시된 대상·항목만 | 허용된 개인 결과보고서 관리 및 허용 범위의 통합 분석보고서 생성·조회·인쇄·관리 | 허용 범위의 운영·계정·배정·소속 관리. 관리자 역할 자체로 모든 조직 접근 권한을 부여하지 않음 | 금지 |
| 고객사 담당자 | 허용된 기업의 진단 진행 현황과 집계만. 개인 응답 원문 금지 | 개인 결과보고서 및 통합 분석보고서 생성·조회·인쇄·관리 금지 | 허용된 기업의 집계 현황만 | 금지 |

보고서 다운로드·인쇄용 API, 내보내기, 변경 이력, 검색·목록·집계도 같은 범위를 적용한다. 상담사 재배정·소속 변경·정지 이후에도 오래된 세션 권한으로 접근하지 못하도록 검증한다. 다른 참가자·기업·상담사 ID 대입으로 범위를 넓힐 수 없어야 한다.

### 보고서 유형별 접근 권한

| 유형 | 참여자 | 상담사 | 관리자 | 고객사 담당자 |
|---|---|---|---|---|
| 개인 결과보고서: 한 참여자, 상담사용 5쪽·내담자용 3쪽 | 직접 조회·인쇄 금지 | 서버 확인 담당 내담자만 조회·인쇄 | 승인된 조직·업무 범위에서 관리 | 접근 금지 |
| 사전·사후 통합 분석보고서: 여러 참여자의 결과·만족도 등 집계 | 접근 금지 | 접근 금지 | 관리자 전용, 서버에서 허용 범위와 집계 모집단 제한 | 접근 금지 |
| 개인별 사전·사후 비교 화면: 한 참여자의 변화, 통합 보고서와 별개 | 미확정 | 미확정 | 미확정 | 개인 결과 접근 금지 정책 적용; 비교 화면의 구체적 권한은 미확정 |

개인별 비교 화면은 REQ-C-010에 따라 유지 여부, 접근 권한과 출력 정책이 미확정이다. 기존 기능의 제거 또는 권한 변경을 이 문서로 확정하지 않는다. 통합 보고서는 REQ-A-006~016을 따른다.

### 서버 권한 검증

1. 업무 API 요청마다 인증된 사용자 식별자를 검증하고 서버가 관리하는 역할·조직·담당 관계와 업무 권한을 확인한다.
2. 상담사의 조회·수정 등은 서버에서 확인한 담당 관계로 제한한다. 관리자 통합 보고서 API는 관리자 역할과 허용된 조직·업무 범위를 모두 확인한다.
3. 브라우저가 전달한 사용자·기업·상담사·참여자 ID는 조회 대상 식별자일 뿐 권한 증거가 아니다. 타인의 ID를 직접 대입해도 데이터가 반환되지 않아야 한다.
4. 조회·인쇄·내보내기·집계 API와 직접 DB/RPC 경로에 같은 접근 제한을 적용한다. 메뉴 숨김이나 URL 분리는 접근 통제가 아니다.
5. 서비스 역할 키 등으로 RLS를 우회할 수 있는 Edge Function도 인증과 대상별 업무 권한을 자체 검증한다. RLS는 DB의 행 접근을 제어하고 서버 검증과 열·응답 제한을 대체하지 않는다.

## 5. 실제 코드 기준 현재 노출 지점

3b-1 완료 작업본을 읽어 확인한 사실이다. 저장소 공개 상태는 사용자 결정에 따르며 이번 작업에서 원격 조회로 재확인하지 않았다.

| 위치 | 현재 동작과 위험 |
|---|---|
| `src/js/05-engine.js` | 계산·캐시 판단·상담사 재계산 규칙을 export하고 설정·피드백 원본을 import. DOM 분리는 완료됐지만 브라우저 실행 가능한 엔진임 |
| `src/js/02-eval-config.js` | 환산식, 판정 함수·경계, 비교군 원본을 export. 개발자 도구에서 확인 가능 |
| `src/data/feedback-*.js` | 전체 코멘트·키워드·분류 매핑이 클라이언트 의존 그래프에 포함됨 |
| `src/index.html`의 import와 `vResult`, `toAssessment` | 브라우저에서 원점수·환산·판정·선택 피드백을 계산하고 보고서를 구성함 |
| `src/index.html`의 저장·로그인 | `sp-demo-v5` localStorage에 `DB`·`ENT` 저장. 클라이언트의 평문 비밀번호 비교와 데모 역할 상태는 인증·권한 통제가 아님 |
| `legacyGlobalValues`, `installLegacyGlobals` | 계산 함수·설정·피드백과 live `DB`·`ENT`·`COUNSELORS`, `S`에 전역 접근 가능. 회귀 검증용 호환성이며 운영 보안 경계가 아님 |

| 공개 저장소·이력·legacy·정답표 | 계산 규칙과 문구를 복원할 자료가 공개된 것으로 취급. 운영 정적 호스트에서 이 자료까지 제공해서는 안 됨 |

현재 작업본은 기능 보존용 개발 프로토타입이다. 실제 개인정보·실제 계정·서버 비밀을 넣어서는 안 되며, 운영 또는 실제 이용자 베타 승인 대상으로 취급하지 않는다. 이번 검토는 전체 저장소·이력의 비밀키/개인정보 스캔을 대신하지 않는다.

### 최신 정책 적용 참고사항 (2026-11-05)

위 표는 3b-1 당시의 역사적 조사이며 이후 작업본 전체의 상태로 덮어쓰지 않는다. ## 6. 서버 전용 계산 아키텍처

4. 보고서에 필요한 환산·판정·선택 피드백·비교 표시 값도 서버가 산출한다. 브라우저는 받은 값을 기존 문자열 템플릿에 표시한다. 오프라인 실패 시 클라이언트 계산으로 우회하지 않는다.

## 7. 데이터 저장 및 API 응답 최소화

- 운영 응답·결과·관계의 원본은 권한 통제된 DB에 보관한다. 브라우저 localStorage에 전체 참여자·기업·계정·평문 비밀번호를 저장하지 않는다. 인증 세션의 저장 방식은 별도 위협 검토로 결정한다.

- 계산 원본·전체 피드백·내부 매핑·불필요한 스냅샷·다른 이용자 데이터는 성공 응답·오류 응답·디버그 로그·CSV/PPT/PDF 메타데이터에도 싣지 않는다.

- REQ-A-006~016의 통합 분석은 서버에서 관리자의 허용된 조직·업무 범위와 모집단으로 제한해 집계하고, 필요한 수치와 표시용 정보만 반환한다. 개인 응답 전체를 브라우저로 보내 프런트엔드에서 집계하지 않는다.
- 통합 집계 조회와 보고서 생성·출력·내보내기는 감사 대상이다. 서버가 관찰할 수 있는 인쇄 요청과 클라이언트 인쇄 실행의 기록 방법 및 실제 인쇄 완료 여부 확인 방법은 구현·검증 시 구분한다. 원문 응답을 감사 로그에 남기지 않는다.
- 자유 의견에는 개인정보가 포함될 수 있어 별도 보호 기준이 필요하다. 소수 집단 재식별 방지와 자유 의견 보호의 익명화·최소 인원·마스킹 기준은 미확정이다. 기준 확정 전 자유 의견 원문이나 소수 집단 식별 가능 정보를 외부 고객사에 제공하는 것으로 정의하지 않는다.
- 보관 대상·목적·기간·삭제 시점·백업 삭제 지연·탈퇴 및 소속 종료 시 처리·법적 보존 예외를 정한다. 상세 수치는 미결정이며 실데이터 베타 전 승인한다.
- 조회·수정·재계산·내보내기·권한 변경의 주체/대상/시각/작업/성공 여부를 감사 기록으로 남긴다. 원문 응답·토큰·비밀번호를 로그에 기록하지 않고 감사 로그 자체의 접근·보관·삭제 권한도 제한한다.

## 9. 서버 이전 시 계산 보존 전략

기존 legacy SHA256 `62fc9dd4c0c0515e204c1697085dec655d59fbac8e495d78676f982d401ad310`과 골든·계약·HTML/JSON·인쇄·시각 기준선을 보존한다. 서버 이전을 이유로 기대값을 수정하지 않는다.

- 점수 합산·환산·판정, 최저 원점수/동점 A>B>C>D>E, 연령대·13번 1순위 분류, 코멘트·키워드 선택 규칙과 알려진 특이점을 그대로 이식한다.
- `resolveResult`: 미완료는 null이며 과거 결과를 지우지 않는다. 기존 키가 같으면 결과를 재사용하고 난수·저장 호출을 추가하지 않는다. 신규·키 변경 시 한 번 계산 후 결과를 저장한다. 기존 `resKey`에 없는 필드를 임의 추가하지 않는다.
- `computeResult`: 선택은 연령(있는 경우) → 목표(있는 경우) → 전문 → 코멘트 순서로 2~4회다. 현 `rint`의 난수 생성·나머지 연산 규칙을 임의 개선하지 않는다. 테스트는 고정 입력 난수와 호출 인자를 대조한다. 서버에서 다른 난수 API를 쓰려면 동일 선택 규약을 검증한다.
- 날짜: `preDate`가 없으면 연령 계산용 `today()`가 먼저 호출되고, 결과 `at`에도 호출된다. `today()`는 UTC ISO 날짜다. 상담사 재계산은 계산·기존 값 덮어쓰기 이후 상담사 얕은 복사, 그 다음 ISO 생성 시각을 기록한다. 변경 이력·updatedAt의 후속 조회 순서도 보존한다. 자정·연도 경계와 시간대, 서버 시계에 따른 영향은 고정 시계/경계 테스트로 확인한다.
- `recomputeResultCore`: 계산은 먼저 정확히 한 번 수행하고 동일 영역 코멘트, 동일 연령대·목표 분류 객체, 기존 전문 키워드를 나중에 덮어쓴다. `old`를 수정하지 않고 동일 객체 참조 재사용과 상담사 `code` 덮어쓰기 순서를 서버 함수 내부 단위 테스트로 보존한다. JSON 통신 전후의 객체 `===`는 보장할 수 없으므로 네트워크 경계에서는 직렬화 값과 저장 결과 재사용을 별도로 검사한다.
- 최초 저장과 재조회·재시도·동시 요청은 트랜잭션/동등한 원자성 및 중복 요청 제어로 한 번 확정한 결과를 다시 추첨하지 않게 한다. 실패 후 재시도의 정책과 동시 편집 충돌은 단계 7에서 명시하고 검증한다.
- 보고서 판정은 현재처럼 열 때 현재 설정으로 계산하고 선택 코멘트·키워드는 저장 결과를 사용한다. 서버 이전 후에도 이 계산을 서버에서 수행한다. `EVAL_VERSION`, 평가/비교 세트 식별자, 생성 시각을 보존한다. 제출 시점 판정 고정으로 바꾸는 결정은 아직 하지 않는다.
- 코멘트는 코드로 문구를 다시 읽고 키워드는 저장 문구를 쓰는 기존 차이, `resultChanged`가 키워드 변경만으로는 true가 되지 않는 특이점도 유지한다. 문구·평가 정책 변경은 기존 별도 승인 절차를 따른다.

모든 항목은 단계 7 구현 후 증거와 함께 검토한다. 기능 테스트 통과만으로 보안 승인을 대신하지 않는다.

1. 네 역할 각각에 대해 Sources·Network·Application/Storage·Console을 검사한다. 엔진 함수·환산/판정 원본·전체 문구·매핑·키·다른 이용자 데이터가 없고, 반환된 본인 허용 내용만 보이는지 확인한다.
2. 운영 산출물과 직접 URL 요청을 검사한다. JS 청크·소스맵·정적 파일·demo/legacy/tests·개발 진입점·공개 Storage·캐시에서 비공개 자료를 얻을 수 없어야 한다. 공개 Git 이력에 이미 있는 자료의 잔여 위험은 별도 기록한다.
3. 무인증·만료/변조 토큰·역할 위조·담당/기업/참가자 ID 바꿔치기·재배정/정지·허용 외 내보내기/집계 요청을 서버 함수와 직접 Data API/RPC 양쪽에서 거부하는지 확인한다. 오류 메시지로 대상 존재나 개인정보를 누설하지 않는다.
4. RLS·열/스키마 권한·뷰·함수·Storage 우회, 특권 서버 경로의 업무 권한 검증을 시험한다. 평문 비밀번호와 서버 키가 저장소·브라우저·응답·로그에 없는지 점검한다.
5. 최초 계산·재조회·미완료·키 변경·상담사 수정의 회귀와 동시 요청·재시도·원자적 저장을 검증한다. 기존 골든·계약·HTML/JSON·인쇄·시각 비교를 통과시킨다. 서버 결과를 신뢰하도록 프런트 테스트 연결을 바꾸는 경우도 기준값은 보존한다.
6. 로그인/계산/내보내기 호출 제한, 세션 종료·권한 변경 반영, 개인정보 최소화·보관/삭제·감사·백업 복구를 검증한다. 세부 수치·세션 정책은 베타 전 확정한다.
7. 공개 저장소·이력의 민감정보와 콘텐츠 권리 검토, 운영/개발 배포 경계, 미결정 보안 정책의 승인 기록, 배포 책임자의 사용자 승인을 확보한다. 중대한 미해결 결함이나 필수 미검증 항목이 있으면 배포하지 않는다.

이번 문서 작업에서는 위 운영 보안 시험을 실행하지 않았다. 3b-1의 회귀 통과 기록은 기능 보존 증거이며 운영 보안 증거가 아니다.

추가 역할·보고서 권한 검증 사례(2026-11-05, 실행 전 기준):

- 상담사 A가 상담사 B의 내담자에 접근하거나 상담사 계정이 관리자 통합 보고서 API를 호출하면 거부한다.
- 참여자의 개인 결과보고서 API 요청, 고객사 담당자의 개인 응답·개인 보고서 및 통합 분석보고서 요청을 거부한다.
- 관리자가 허용되지 않은 다른 조직의 통합 보고서를 요청하면 거부하고, 허용된 관리자는 허용된 조직의 통합 보고서를 조회할 수 있다.
- 보고서 조회·생성·인쇄·내보내기의 감사 기록이 정책대로 생성되는지 확인하고, 실제 인쇄 완료와 시스템이 관찰한 인쇄 요청을 구분한다.
- 직접 DB/RPC 경로에서 서버 API의 접근 제한을 우회하지 못하는지 확인한다.

위 사례는 목표 검증 항목이며 이번 문서 작업에서 실행하거나 통과 판정하지 않았다.

### STEP 14-A 고객사 마스터 접근 경계 (2026-11-06, SQL 미적용)

`secondcareer-admin-companies`는 공용 `authenticateAdmin`으로 서버 프로필의 역할·운영 조직을 확인하고 모든 목록·상세·수정에 해당 `organization_id`를 강제한다. 고객사 ID는 조회 키이며 권한 근거가 아니다. 요청의 조직·생성 시각 등 임의 필드는 거부한다. 목록은 PM 이름만, 상세는 관리에 필요한 PM 연락처를 제공하며 원문 요청이나 PM 정보를 로그에 기록하지 않는다. 수정은 마지막 조회 `updated_at`을 비교하여 동시 변경 덮어쓰기를 거부한다.

미적용 `supabase/proposals/client-companies.sql`은 새 테이블에 RLS를 활성화하고 PUBLIC·anon·authenticated의 직접 접근 권한을 회수한다(허용 정책 없음). 서비스 역할에만 SELECT와 지정 열 INSERT/UPDATE를 부여하며 DELETE 권한은 부여하지 않는다. 서비스 역할은 RLS를 우회하므로 서버의 조직 필터가 필수다. 이 제안의 실제 권한·트리거·제약 검증과 적용 승인이 있어야 배포할 수 있다. 운영 DB·Auth·기존 참여자·진단 데이터는 이 단계에서 변경하지 않는다. 고객사 마스터 등록은 고객사 담당자 계정이나 참여자 ID 연계 권한을 만들지 않는다.

### STEP 14-B1 고객사 ID 연결 경계 (2026-11-06, SQL·배포 미적용)

관리자의 선택형 등록만 `companyId`를 받는다. 서버 프로필의 organization_id와 같은 활성 고객사를 먼저 검증하고, 입력 기업명이 있으면 name_key와 같은 공백·영문 대소문자 정규화로 대조한다. 기록할 기업명은 마스터에서 가져온다. 상담사는 기존 본인 담당 문자열 등록만 유지하며 ID 등록 요청은 거부한다. 고객사 담당자 역할·계정·등록 권한은 추가하지 않는다. 고객사 담당자는 허용 고객사의 집계 현황 조회 전용이며 참여자·고객사·계정 쓰기, 개인 응답/보고서와 통합 분석보고서 접근은 금지한다.

미적용 `participant-company-link.sql`은 NULL 허용 company_id와 `(organization_id,company_id)` 복합 FK, 관련 인덱스를 추가한다. 기존 company_name·NULL 참여자·RLS 정책은 보존하고 클라이언트의 직접 ID 변경은 트리거로 차단한다. 기존 등록 RPC는 대체하지 않으며 연결 전용 service_role RPC에서 관리자·동일 조직 상담사·고객사 활성 상태를 다시 검증한다. 요청 행 잠금과 고객사 행 잠금 안에서 프로필·로그인 매핑·참여자·완료 기록을 원자적으로 연결한다. 기존 RPC가 ID 요청을 잘못 처리하면 완료 트리거가 롤백시킨다. 실제 RPC·트리거·Auth 훅 정의 및 권한과의 충돌 여부는 적용 전 확인해야 한다. 충돌 시 기존 제약을 제거하지 않고 전체 트랜잭션을 실패시킨다.

Auth 생성은 외부 API라 DB 트랜잭션과 원자적이지 않다. 완료 응답이 불명확하면 동일 요청 잠금을 사용하는 복구 RPC로 완료/취소를 확정한다. 완료면 동일 연결을 확인하고 성공을 반환하며, 취소면 늦은 완료를 차단한 뒤 이번 호출이 생성한 새 Auth만 정리한다. 기존 계정은 삭제하지 않는다. 복구·정리 실패나 Auth 생성 응답 자체가 불명확한 경우 새 Auth가 남을 수 있으며, 요청 예약을 유지해 자동 재시도를 차단하고 별도 운영 확인이 필요하다. 비밀번호·원문 요청·PM 연락처를 로그에 기록하지 않는다.

고객사 상세는 해당 조직의 ID 연결 건수와 조직 전체 company_id NULL 건수만 반환하며 개인 레코드는 반환하지 않는다. 두 조회 시점의 차이가 있을 수 있어 트랜잭션 스냅샷 합계로 보장하지 않는다. 기존 company_name 현황·보고서 필터는 그대로다. 이관 SQL은 읽기 전용 후보/인원 확인용이며 조직 내 정규화 정확 일치만 후보가 되고 공백·불일치·모호성은 미연결로 남긴다. 후보도 자동 승인/연결하지 않는다. 실제 DB locale/POSIX 공백 판정·FK·권한·동시성은 미검증이며 운영 SQL·배포는 실행하지 않았다.

## 12. 남은 보안 의사결정

- Auth 로그인·초대·계정 복구·최초 비밀번호 설정, 관리자/상담사 강화 인증, 세션 저장·수명·철회와 요청 제한 수치.
- 사용자/역할/기업/담당 관계의 DB 모델, 관리자 업무 권한의 세분화, 재배정·정지·퇴사 후 접근 정책.
- 고객사에 허용할 개인 단위 항목과 집계 대상, 소수 집단 비식별 기준은 미결정이다. 다만 개인 응답 원문과 개인 결과보고서 접근은 2026-11-05 결정에 따라 금지한다. 내담자 직접 결과 열람은 현재 금지 정책을 유지하며 변경은 별도 승인.
- 개인정보 고지·보관 기간·삭제/백업 정책·감사 보관 기간과 담당자, 데이터 리전·호스팅·복구 목표.
- 공개 유지에 따른 과거 엔진·콘텐츠·캡처·작성자 정보 노출의 권리 검토 및 잔여 위험 승인. 이력 재작성은 별도 승인 없이는 하지 않음.
- 향후 기밀 서버 코드/데이터의 접근 통제 저장 위치·배포 경로, 서버 함수 실행 방식·DB 권한·운영 키 관리 체계.
- 동시 편집·중복 제출·네트워크 실패 재시도의 상세 계약. 평가 규칙 변경 후 과거 판정 정책과 코멘트/키워드 재출력 정책은 기존 미결정 상태 유지.
